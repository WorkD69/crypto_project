# Этап 0 после исправлений: Telegram Watcher → Hermes

> Публичная редакция: локальные идентификаторы и приватные сведения удалены; исходный отчёт хранится только локально.

17.10.2026, Windows. Итог **PARTIAL**: технический путь для одного собственного текстового события проверен живым Telegram и действующим Hermes. Стабильность 24/7, полнота синхронизации Telegram Web, перенос авторских событий и медиа в Hermes пока не доказаны. Расписание не включено; три авторских источника остаются `enabled=false`.

## Причины ошибок и изменения

**Сообщение находилось со второго запуска.** В исходном коде ожидалась первая видимая запись и фиксированные 800 мс, после чего выполнялся обход DOM. Живая диагностика наблюдала список из кэша, пока в заголовке Telegram Web несколько секунд отображалось `updating`. Кроме того, финальная сверка хвоста обновляла только ID, уже попавшие в первоначальный снимок; новый ID из поздней синхронизации отбрасывался. Старые журналы не сохраняли точный момент обновления UI, поэтому это подтверждённые дефекты и правдоподобное объяснение конкретного запуска, но не точная реконструкция серверной последовательности. Теперь Watcher ждёт ухода видимой занятости и стабильного хвоста, сверяет его повторно и включает новые ID. Если UI не готов, возвращается `SYNC_UNCONFIRMED`, курсор не продвигается. `UI_READY` не является серверным подтверждением: поле `server_sync_confirmed=false` и предупреждение выводятся явно.

**Четыре фотографии скачивались снова.** Старый цикл вызывал загрузку для каждого наблюдаемого вложения до исчерпания лимита; повторное использование файла применялось только после этого лимита. Теперь при прежнем составе вложений файл переиспользуется после проверки пути, наличия и SHA-256. При повреждении он загружается заново; `--recheck-media --message-id` запускает адресную перепроверку. Смена JPEG-байтов/разрешения сама по себе не создаёт новую версию: вариант фиксируется для проверки. Версию создаёт изменение видимого текста или состава вложений.

Сохранены выделенный Playwright-профиль, UI-адаптер, курсоры по источникам, SQLite, неизменяемые версии, outbox, загрузка медиа, прежний Qwen pipeline, рыночные Python-компоненты и торговый дневник. Watcher лишь обнаруживает, сохраняет и передаёт событие. Он не принимает торговых решений и не вызывает LLM на обычном проходе.

## Очередь и проверенный путь

Таблицы `events` и `event_history` добавлены в существующую SQLite Watcher. Запись сообщения и создание `NEW`/`EDITED` происходят в одной транзакции. Уникальность `(source, message_id, version)` и устойчивый SHA-256 ключ не допускают второго задания на ту же версию. Состояния: `DETECTED` (в истории), `WAITING`, `DELIVERED` (попытка передачи), `ACCEPTED` (ответ с тем же ключом проверен), `COMPLETED`, `RETRY`, `NEEDS_REVIEW`. Захват атомарен и имеет lease; истёкшая попытка с неизвестным исходом переходит в `NEEDS_REVIEW` без слепого повторного вызова. Тестовый суточный бюджет Luna резервируется внутри транзакции SQLite до отправки.

`handoff` по умолчанию записывает только приватный JSON события в `%LOCALAPPDATA%\CryptoResearchPlatform\browser-collector\handoff` и не вызывает Hermes. Payload `crypto.event.v1` содержит один источник, наблюдаемые ID/версию/время, текст, хеш, признаки изображений/видео и ссылки на локальные файлы; профиль браузера, токены и архив канала не передаются. `content` достаёт конкретную версию по запросу. Единственный реализованный живой адаптер ограничен собственным текстом с префиксом `CRP-STAGE0 HERMES-FIRST`: существующий `hermes chat` CLI вызывается по уже настроенному SSH без изменения Hermes. Он использует Luna, низкое reasoning, один ход, ограниченный бюджет и `--ignore-rules` (в установленной v0.21.6 пропускает личную память и файлы контекста). Ответ сверяется с ключом события и сохраняется локально. Это проверка минимального интерфейса, а не готовая доставка произвольных авторских публикаций.

Существующий `local-jobs` пригоден для коротких текстовых задач, но текущий контракт ограничен текстом примерно 5000 символов и не подтверждает поддержку изображений, видео и идемпотентных заданий. Поэтому медиа не отправлялись через него. Передача текста через установленный CLI уже технически возможна без правки конфигурации Hermes; автоматический агентный процесс для авторских событий и медиа остаётся отдельной работой.

## Источники, медиа и следующий узкий шаг

Два публичных источника ранее подтверждены видимым полем Link и Web peer. Для Крипто Ильи кандидат с похожим заголовком имеет peer `PRIVATE_CHANNEL_PEER`, но соответствие инвайту не доказано. Официальная страница инвайта дала ссылку «Open in Web»; при прямом переходе авторизованный Telegram Web A убрал `tgaddr` и открыл корень приложения, не показав peer канала. Статус остаётся `NEEDS_BINDING`; этот кандидат не включён. Нужна проверка по самой видимой карточке канала с инвайтом или другой допустимой явной связи invite→peer, без вступления/сбора по одному названию.

Текст передаётся напрямую. Для фото/видео контракт очереди передаёт относительные ссылки и SHA-256, но VPS Hermes не умеет прочитать эти Windows-файлы напрямую. Следующий технический шаг после согласования границы доступа: узкий запрос конкретного разрешённого вложения по `event_key`/версии с проверкой SHA-256 через имеющийся защищённый канал Tailscale/SSH, либо локальная Qwen/Whisper на Windows с передачей Hermes только результата, таймкодов и ссылок на кадры. Большие файлы в промпт не помещать. Новая Whisper-модель и полноценная обработка видео на этом этапе не устанавливались. Минимальные будущие инструменты Hermes: `get_event`, `get_media`, `run_qwen`, `run_whisper`, `find_author_rules`, `get_bybit_candles`, `check_factor`, `save_idea`, `create_draft`, `idea_status`. Сейчас проверена только передача одного текстового события через CLI; остальные пункты являются интерфейсным контрактом, не готовыми инструментами. Численные проверки остаются в Python.

Watcher работает лишь при включённом Windows-ноутбуке и доступном Telegram Web. Кэш Web UI, невидимые старые правки и долгие пропуски остаются ограничениями. На текущем VPS (1 vCPU/2 ГБ/15 ГБ вместе с Hermes) Chromium не устанавливался, 24/7 Telegram не заявляется. Ближайший прототип может расширить проверенный CLI-адаптер до разрешённого авторского текста и валидируемого ответа Hermes `next_action`, а Qwen/Whisper запускать на Windows по этому ответу: конфигурация Hermes для такого пути не меняется. Если нужен прямой запрос исходных файлов с VPS, потребуется отдельный проектный инструмент в Hermes и защищённый транспорт по Tailscale/SSH; точную правку действующей конфигурации следует подготовить и согласовать до применения. Сначала нужно подтвердить точную привязку приватного источника, затем отдельно согласовать включение авторских событий и способ точечной передачи медиа. До этого оставлены собственный тестовый источник, ручной импорт и dry-run.
